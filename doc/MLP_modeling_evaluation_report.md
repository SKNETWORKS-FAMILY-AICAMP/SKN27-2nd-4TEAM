# 모델링 평가·분석 보고서

**대상:** `src/modeling/MLP.ipynb` 기준 MLP(다층 퍼셉트론) 이진 분류 파이프라인  
**데이터:** `data/dataset.xlsx`, 타깃 `Churn`  
**작성 목적:** 학습·검증 절차, **기법 선택 근거**, **모델 성능**, 지표 해석, 누수·신뢰성 점검 요약

---

## 1. 실험 설정

### 1.1 데이터 분할

| 항목 | 내용 |
|------|------|
| 방법 | `train_test_split` |
| 비율 | 테스트 20% (`test_size=0.2`) |
| 층화 | `stratify=y` (이탈 비율 유지) |
| 시드 | `random_state=42` |

**시간 기반 평가 (한계):** `data/dataset.xlsx`에는 **관측 일자·스냅샷 시각·가입일 등 “진짜 시간축”을 나타내는 컬럼이 없다.** 그래서 **과거 구간만으로 학습하고 미래 구간만으로 검증하는 방식의 본격적인 시간 기반 홀드아웃 평가는 이 데이터만으로는 수행할 수 없다.**  
이 보고서의 주요 지표는 위 **무작위·층화 분할** test에 대한 결과이며, **“미래 시점 일반화”나 “시간 누수 없음”을 증명하지 못한다.**

**보조 참고 (선택):** 저장소의 `scripts/time_holdout_mlp_eval.py`는 `CustomerID` 오름차순으로 앞 80% / 뒤 20%를 나누는 **순서 프록시 실험**이다. ID가 실제 시간 순서와 일치한다는 가정이 없으면 **시간 기반 테스트를 대체할 수 없고**, 수치는 참고용이다.

### 1.2 전처리·모델 파이프라인 (요약)

1. 결측: `CJ_MissingValue` / `JH_train_stats` + `JH_MissingValue` (`src/pipeline/missing_value.py`)
2. 이상치·변환: `OutlierControl` (`src/pipeline/outlier_control.py`)
3. 파생 피처: `FeatureCreate` (`src/pipeline/features.py`) — 테스트 시 train에서 계산한 `MonthlyOrderFreq` 평균 전달
4. 스케일링: `StandardScaler` — **train에 `fit`, test는 `transform`만**
5. 모델: `sklearn.neural_network.MLPClassifier`, `max_iter=500`
6. 튜닝: `GridSearchCV` — `cv=3`, `scoring='f1'`, `n_jobs=-1`

### 1.3 하이퍼파라미터 탐색 공간

| 파라미터 | 후보 |
|----------|------|
| `hidden_layer_sizes` | `(64, 32)`, `(100,)`, `(50, 50)` |
| `alpha` | `1e-4`, `1e-3`, `1e-2` |
| `learning_rate_init` | `0.001`, `0.01` |

최적 조합은 노트북 실행 시 `grid.best_params_`로 확인한다. (저장된 실행 예: `alpha=0.0001`, `hidden_layer_sizes=(50, 50)`, `learning_rate_init=0.01` 등)

### 1.4 기법 선택 이유

아래는 **본 파이프라인에서 해당 기법을 쓴 설계 근거**이다. “유일한 정답”이 아니며, 운영·데이터가 바뀌면 로지스틱·트 기반 부스팅 등 **베이스라인과의 비교**를 권장한다.

| 선택 | 이유 |
|------|------|
| **`MLPClassifier`** | 이탈 예측은 **수치·파생 특성 간 비선형 상호작용**(예: 공백·빈도·만족도 조합)이 큰 편이다. **은닉층이 있는 MLP**는 이런 결합을 데이터로부터 학습하기에 적합한 후보다. `sklearn` 내장이라 **재현성**(`random_state`)·파이프라인 연동이 단순하다. **단점·전제:** 해석력은 트 모델보다 낮고, **스케일 정규화**에 민감하다 → `StandardScaler`와 함께 쓴다. |
| **`StandardScaler`** | 신경망은 입력 스케일에 민감하다. **train만으로 평균·분산 추정** 후 test는 `transform`만 적용해 누수를 막는다. |
| **`GridSearchCV`** | 탐색할 하이퍼파라미터가 **소수·이산 그리드**(은닉층 구조, `alpha`, `learning_rate_init`)로 정해져 있어, **전수 조합 탐색**이 가능하다. 구현이 단순하고 결과가 **재현·보고**하기 쉽다. 조합 수가 커지면 `RandomizedSearchCV` 등으로 바꾸는 것이 일반적이다. |
| **`cv=3`** | train을 세 폴드로 나눠 검증 오차를 추정한다. **5-fold**보다 계산은 적고, 데이터 규모가 크지 않을 때는 **3-fold**도 자주 쓴다. (더 안정적인 추정이 필요하면 `cv=5`로 올릴 수 있다.) |
| **`scoring='f1'` (튜닝)** | 이탈은 **소수 클래스**(약 15~17%)라 **정확도만** 보면 다수 클래스에 치우친 모델이 유리해질 수 있다. **F1**은 정밀도·재현율의 균형을 맞춘 지표로, **불균형 이진 분류**에서 튜닝 목표로 쓰기 적합하다. (비용이 불균형이면 `f1` 대신 가중치·별도 scorer 설계 가능.) |
| **`stratify=y` (분할)** | train/test에서 **이탈 비율**을 비슷하게 유지해, 분할만으로 클래스 비율이 크게 흔들리지 않게 한다. |
| **층화 무작위 test (§1.1)** | **시간 컬럼이 없어** 진짜 시간 홀드아웃은 불가하므로, **일반화 점검**을 위해 우선 홀드아웃 test 지표를 본다. 시간 일반화는 **기준 시점 컬럼** 확보 후 별도 설계할 것(§1.1). |

**정리:** MLP는 **비선형 표 형태 데이터**에 대한 실용적 선택이고, GridSearch는 **작은 그리드**에 대한 **전수·재현 가능한 튜닝**이다. 최종 모델 선정은 **운영 비용(오탐 vs 미탐)** 과 **다른 알고리즘과의 벤치마크**로 확정하는 것이 바람직하다.

## 2. 평가 지표 (테스트 세트)

노트북에서 **확률** `y_prob = predict_proba(...)[:, 1]`와 **임계값** 기반으로 다음을 산출한다.

### 2.1 구분 성능 (랭킹)

| 지표 | 의미 |
|------|------|
| **ROC-AUC** | 이탈 확률 순위가 실제 이탈과 얼마나 일치하는지 (임계값 무관) |
| **Average Precision (PR-AUC)** | 불균형 데이터에서 PR 곡선 아래 면적; “이탈” 클래스에 대한 순위 품질 |

### 2.2 임계값 의존 지표 (기본 0.5)

| 지표 | 의미 |
|------|------|
| **Precision (정밀도)** | “이탈로 예측”한 것 중 실제 이탈 비율 |
| **Recall (재현율)** | 실제 이탈 중 모델이 잡아낸 비율 |
| **Specificity (특이도)** | 실제 비이탈 중 비이탈로 맞춘 비율 |
| **F1** | 정밀도·재현율의 조화평균 |

### 2.3 혼동행렬·리포트

- **혼동행렬:** 행=실제 클래스, 열=예측 클래스 (0/1)
- **`classification_report`:** 클래스별 precision / recall / f1-support

### 2.4 임계값 스윕

- 임계값을 구간(예: 0.05~0.95)에서 바꿔가며 Precision, Recall, F1을 표로 출력
- **F1이 최대인 임계값**을 별도 표기 — 비용 구조에 따라 운영 임계값은 0.5가 아닐 수 있음  
  (예: 놓치면 안 되는 경우 재현율 우선 → 임계값 낮춤, 오탐 비용이 크면 정밀도 우선 → 임계값 높임)

## 3. 모델 성능

### 3.1 모델·튜닝 설정

| 항목 | 내용 |
|------|------|
| 추정기 | `MLPClassifier` (`max_iter=500`, `random_state=42`) |
| 튜닝 | `GridSearchCV` — **교차검증 점수는 F1** (`scoring='f1'`), 3-fold |
| 의미 | 검증 폴드에서 **이진 F1**이 최대가 되도록 하이퍼파라미터를 고른다. **테스트 ROC-AUC는 튜닝 목표에 직접 들어가지 않는다.** |
| 최종 평가 | `grid.best_estimator_`로 **전체 train**에 재적합된 모델을 **홀드아웃 test**에서 평가 (노트북 기준). |

### 3.2 홀드아웃 테스트 성능 (참고 수치)

**분할:** §1.1의 **무작위·층화** test (표본 수 약 1126건, 전체 이탈 비율과 유사).  
재현 시 소수점은 환경에 따라 달라질 수 있다.

**A. `MLP.ipynb`에서 산출한 예시 (임계값 0.5, 동일 파이프라인)**

| 지표 | 참고 값 |
|------|---------|
| Precision | ~0.75 |
| Recall | ~0.81 |
| Specificity | ~0.95 |
| F1 | ~0.78 |
| ROC-AUC | ~0.95 |
| PR-AUC (Average Precision) | ~0.85 |
| 혼동행렬 (예시) | 비이탈·이탈 혼동 규모는 노트북 출력 참고 |



**B. 동일 전처리·동일 그리드로 스크립트 재현 시 (층화 분할, 시드 42)**

| 지표 | 참고 값 |
|------|---------|
| CV 최선 F1 (3-fold 평균) | ~0.77 |
| 테스트 ROC-AUC | ~0.97 |
| 테스트 F1 (임계값 0.5) | ~0.82 |
| 최적 파라미터 (해당 실행) | `alpha≈0.001`, `hidden_layer_sizes=(50,50)`, `learning_rate_init≈0.01` 등 |

**임계값:** 기본 0.5 외에, 확률 임계값을 바꿔 **F1 최대**에 가까운 지점(예: **~0.65** 부근에서 P≈R≈0.79 수준)을 쓰면 정밀도·재현율 균형을 맞출 수 있다(노트북 임계값 스윕 셀).

### 3.3 성능에 대한 해석 (요약)

- **순위·확률 품질:** ROC-AUC·PR-AUC가 모두 높은 편이면, **이탈 확률 순위**가 실제 이탈과 잘 맞는다고 볼 수 있다.
- **임계값 0.5:** 재현율이 정밀도보다 다소 높게 나오는 경향이 있으면, **실제 이탈을 놓치지 않는 쪽**에 가깝게 맞춰진 것으로 읽을 수 있다(비용 가정과 맞는지 검토).
- **클래스 비율:** 이탈이 소수 클래스(대략 **15~17%**)이므로, 정확도만 보면 낙관적으로 보일 수 있다. **F1·PR-AUC·혼동행렬**을 함께 본다.
- **한계:** §1.1과 같이 **시간축 검증이 없으면** “운영 시점·미래 데이터”에서의 성능은 본 절의 수치만으로 단정하지 않는다.

### 3.4 민감도·대조 (요약)

| 실험 | 요지 | 참고 결과 |
|------|------|-----------|
| 라벨 셔플 | train 라벨만 무작위로 섞어 재학습 | test ROC-AUC가 **~0.46** 수준으로 떨어짐(우연에 가까움) → 라벨과의 연결이 깨지면 성능이 사라짐 |
| 누수 의심 피처 드롭 | 일부 행동·금액 관련 파생 제거 후 재학습 | 상세 수치·드롭 목록: `doc/feature_engineering_validation_report.md` **7.3** |

## 4. 신뢰성·누수 점검 요약

| 검사 | 내용 | 결과 요약 |
|------|------|-----------|
| 스케일러 | train만 fit | 적절 |
| JH 결측 | 통계는 train에서만 산출 후 train/test 동일 적용 | 적절 |
| 파생 피처 | `Stagnant_Loyal` 등 train 평균만 test에 전달 | 적절 |
| 이상치 | 고정 clip·log (train 분포로 임계값 추정 없음) | 전처리 누수 해당 없음 |
| 라벨 셔플 | train 라벨만 무작위 섞어 재학습 후 test 평가 | 저장된 실행 예: test ROC-AUC **≈0.46** (우연 수준). 실제 라벨 학습 대비 무의미하게 하락. **누수 의심 피처 제거 대조 실험 수치**는 `doc/feature_engineering_validation_report.md` **7.3** 참고 |

**주의:** 지표가 높다고 해서 **도메인 누수(타깃 정의와 동시에 관측되는 변수 등)** 가 없다고 증명되지는 않는다. 컬럼 정의·수집 시점은 `doc/columns.md` 및 요구사항 문서와 함께 검토할 것. **시간 컬럼이 없으면 시간 일반화·미래 성능은 본 문서의 test 지표만으로 판단할 수 없다.**
